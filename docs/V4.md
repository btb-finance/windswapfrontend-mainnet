# Wind Swap v4 on NEAR testnet

The `/v4` routes add the Wind Swap v4 DEX (NEAR testnet) next to the existing EVM pages. The
EVM pages are unchanged apart from one addition: Base Sepolia (84532) is in the wagmi chain list.
The NEAR wallet only loads under `/v4`. Under `/v4` the global chain guard does not switch the
wallet to Base, so a Base Sepolia deposit stays on Base Sepolia.

The v4 pages act for one of two wallets, chosen with the NEAR / EVM switch in the header:

- **NEAR**: a NEAR testnet account. Each action is a direct contract call from that account.
- **EVM**: a MetaMask (or other injected) wallet, for EVM-only users with no NEAR account. Each
  action is turned into a `SignedAction`, signed with `personal_sign`, and then sent to a relayer
  that calls `execute`. The relayer pays the NEAR gas.

The owner id (64 hex digits) is what the contract keys balances, positions, stakes, withdrawals and
veNFTs by. For a NEAR account it is `sha256(account id)`. For an EVM wallet it comes from
`resolve_wallet("evm:0x…")`. The owner views (`get_*_of_owner`) take this id, so both wallet types read
the same state.

## Pages

| Route | What it does |
|---|---|
| `/v4` | **One-click swap** (default). NEAR: one `ft_transfer_call` on the input token, with the swap message. EVM: a signed swap intent, then the deposit on Base Sepolia, with a progress tracker. Route options and live quotes (`quote_exact_input`), min. received from SwapSettings slippage. **Advanced (use DEX balance)** keeps the old flow (`swap_exact_input` from the DEX balance). Both modes. |
| `/v4/pools` | Pools whose two tokens are whitelisted: pair, fee, tick spacing, price (token1 per token0), current tick, liquidity. Below them, the **Solvency** panel (`get_all_tokens_accounting`). |
| `/v4/liquidity` | Price range (min/max price -> ticks aligned to spacing), shared by two tabs. **One token** (default): a zap that adds liquidity from a single token (NEAR: one `ft_transfer_call` with `add_liquidity`; EVM: an `AddLiquidity` intent and a Base deposit). **Two tokens (advanced)**: amounts derived from liquidity, minted from the DEX balance. Remove (`burn_position`) and collect, for the position of the chosen range (`get_position_of_owner`). Both modes. |
| `/v4/portfolio` | DEX balances of the owner (`get_balances_of_owner`), in both modes. Wallet balances, storage registration, deposit (`ft_transfer_call`) and withdraw are NEAR-only, with a notice in EVM mode. |
| `/v4/bridge` | EVM only. Deposit ETH or test1 on Base Sepolia to the vault (`0xaa81…259e`), with a balance that updates when the relayer credits it. Withdraw with a signed `WithdrawEvm`. The **Withdrawals** list is `get_withdrawals_of_owner` (status Pending, Signed, Broadcast or Failed, with a Basescan link). |
| `/v4/lock` | Create a WIND lock (1 week to 4 years, rounded to weeks), optionally **permanent** in the same step. For each veNFT: add WIND, extend, withdraw when expired, split, merge, make permanent or unlock. Shows voting power and whether it voted this epoch. Both modes. |
| `/v4/vote` | Gauges from `get_gauges`, with each veNFT's votes, vote allocation (percent, total 100), reset, poke, fee and bribe claims. The bribe form takes its token from a dropdown of `get_bribe_tokens`. Both modes. |
| `/v4/rewards` | Epoch countdown (`get_epoch`) with a **Distribute** button once the epoch has passed. Works in both modes (EVM signs `"Distribute"`). Rebase claims per veNFT. Liquidity positions from `get_positions_of_owner`, with stake, claim and unstake per range. Both modes. |

`/v4` (Swap) works in both modes; its balances are read by owner. `/v4/portfolio` deposit and withdraw
are NEAR-only. One-click swaps and zaps use the wallet's own balance (NEAR wallet, or Base Sepolia for
EVM), not the DEX balance.

## Code layout

- `src/lib/windswap-v4/`: copy of the SDK source (`sdk/src`) at commit `e3e049a` of
  github.com/btb-finance/WindSwapV4. Import suffixes `.js` were dropped for the Next bundler.
- `src/lib/v4/config.ts`: contract id, RPC, token list, pool probe limit.
- `src/lib/v4/near.ts`: wallet-selector transaction conversion, `storage_deposit` action, readable error mapping
  (`readableNearError`: contract panics and engine error names to sentences).
- `src/lib/v4/routes.ts`: candidate routes (direct pools and two-hop pool routes).
- `src/lib/v4/owner-views.ts`: the contract v7 owner views (positions, stakes, withdrawals, balances,
  bribe tokens, gauges, accounting). List views are paged by 100.
- `src/lib/v4/intents.ts`: one-step builders pinned by `npm run check:v4-intents`. The `Swap` and `AddLiquidity`
  intents (key order fixed), the signed intent and cancel messages, the NEAR `ft_transfer_call` messages
  (`{swap:{path,min_amount_out,to}}`, `{add_liquidity:{…,zap:true,min_liquidity}}`), and `parseIntentState`
  for `get_intent`. No runtime imports, so the node check can load it.
- `src/hooks/v4/useV4Intents.ts`: the EVM intent flow (sign, `POST /v1/intent`, Base deposit, polling of
  `get_intent` and the payout withdrawal, cancel). `useBaseBalance` reads the Base Sepolia balance.
- `src/components/v4/V4IntentTracker.tsx`: the progress card (Signed, Deposit sent, Credited, Swapped / Position
  minted, Payout broadcast) with Basescan links, retry deposit, cancel and the copy-JSON panel.
- `src/components/v4/V4ZapAdd.tsx`: the one-token liquidity form (`/v4/liquidity`, One token tab).
- `src/lib/v4/evm/signed.ts`: `SignedAction` builders. `toSignedAction(call)` maps a NEAR method name to its
  variant with fields in the Rust declaration order. `actionMessage` builds the exact string the wallet signs.
  `distribute` maps to the unit variant `"Distribute"`. `create_lock` writes `permanent` only when true.
- `scripts/check-v4-signed.mts`: node check of the signed JSON against serde's output (`npm run check:v4-signed`).
- `src/lib/v4/ve/calls.ts`: ve(3,3) and swap/liquidity calls as `FunctionCallAction`s. The same call runs
  in NEAR mode (direct) or EVM mode (signed), depending on the active wallet.
- `src/lib/v4/ve/views.ts`, `loaders.ts`: read views for locks, gauges, epoch, claims, balances and withdrawals.
- `src/lib/v4/relay.ts`: POST to the relayer: `execute` (signed actions), `/v1/intent` and `/v1/intent/cancel` (intents).
- `src/providers/V4ActorProvider.tsx`: the active wallet (NEAR or EVM mode), owners, `run` (send or sign),
  and the last signed payload. `useV4Send` (swap, liquidity, lock, vote, rewards) routes through it.
- `src/components/v4/V4ModeSwitch.tsx`, `V4WalletGate.tsx`, `V4SignedPayload.tsx`: header switch, connect gate,
  and the copy-JSON panel for signed actions.
- `src/components/v4/V4Solvency.tsx`: per-token accounting table with the migrated note.
- `src/components/v4/V4Bridge.tsx`, `V4Lock.tsx`, `V4Vote.tsx`, `V4Rewards.tsx`: the ve(3,3) and bridge pages.
- `src/lib/v4/liquidity.ts`: price range to tick, amount to liquidity conversions.
- `src/providers/NearWalletProvider.tsx`: wallet-selector (My NEAR Wallet, Meteor, HERE), testnet.
- `src/app/v4/layout.tsx`: wraps the v4 routes with the NEAR provider and the v4 header.
- `src/hooks/v4/`: market (tokens and pools), balances (by owner), and send (pending state, errors, toasts).

## Config

Edit `src/lib/v4/config.ts`:

- `V4_CONTRACT_ID` (default `windswapv4-btb.testnet`)
- `V4_RPC_URL` (default `https://rpc.testnet.near.org`)
- `V4_TOKENS` (token account ids, symbols, decimals)
- `V4_POOL_PROBE_MAX` (pool ids probed for the pool list. The contract has no pool count view. Gauges come from `get_gauges`)
- `V4_EVM_CHAIN_ID`, `V4_VAULT_ADDRESS`, `V4_TEST1_ADDRESS`, `V4_INTERNAL_TOKENS` (Base Sepolia bridge and token ids)

Environment:

- `NEXT_PUBLIC_V4_RELAY_URL` (optional): the relayer base URL. The app posts `execute` to it, and intents to
  `<base>/v1/intent` and `<base>/v1/intent/cancel`. Not built yet. Unset, every EVM action (including an
  intent) shows its signed payload with a **Copy relay JSON** button for an operator to submit. Never put a
  private key in the frontend.

No other environment variable is needed. `NEXT_PUBLIC_CONVEX_URL` is not used (Convex was removed), so
`npm run build` passes without it.

## EVM mode: signing and relay

1. The wallet signs (EIP-191 `personal_sign`):
   `Wind Swap v4 action on windswapv4-btb.testnet by evm:0x<lower> nonce N expires T: <action JSON>`.
   The action JSON is `serde_json::to_string` of the contract's `SignedAction`: externally tagged, fields
   in declaration order, no spaces, amounts as strings. Examples:
   `{"Vote":{"token_id":1,"pools":[4,1],"weights":["70","30"]}}`,
   `{"CreateLock":{"amount":"20000000000000000000","duration":2419200,"permanent":true}}`,
   `"Distribute"` (a unit variant is a bare string). `CreateLock.permanent` is left out when false.
2. The nonce is unique per wallet (millisecond time plus a random part). `expires` is now + 600 s.
3. The relayer receives `POST NEXT_PUBLIC_V4_RELAY_URL` with
   `{"contractId":"windswapv4-btb.testnet","method":"execute","args":{"wallet","action","nonce","expires","signature"}}`.
   It calls `execute` with those args from a NEAR account it controls and returns
   `{"txHash"?, "result"?, "error"?}`. `result` is the contract's `ActionResult`.

Run `npm run check:v4-signed` after changing `signed.ts`. It compares the JSON with the strings serde
produces in `crates/near-contract/src/tokenomics_tests.rs`.

The signing path was checked outside the app: the canonical JSON of the sample actions matches the
Rust shape, and a signature from a test key recovers to its address.

## One-step flows (intents and ft_transfer_call)

**NEAR wallets.** One transaction: `ft_transfer_call(receiver_id = DEX, amount, msg)` on the input token, with
1 yoctoNEAR and 200 TGas (`V4_NEAR_FT_CALL_GAS`). `msg` is the JSON string:

- Swap: `{"swap":{"path":[{"pool_id","token_in"}…],"min_amount_out":"…","to":"near:<account>"}}`. The output
  goes straight back to the wallet. If the swap fails, the token contract refunds the input.
- Zap (add liquidity from one token): `{"add_liquidity":{"pool_id","tick_lower","tick_upper","zap":true,"min_liquidity":"…"}}`.
  The position is minted for the sender. Leftover dust stays in the DEX balance.

The output token of a NEAR swap must be registered for the wallet (Portfolio, storage). The swap card blocks
the swap and says so when it is not.

**EVM wallets (intent).**

1. Sign with `personal_sign`: `Wind Swap v4 intent on <contract> by evm:0x<lower> nonce N expires T: <intent JSON>`.
   The intent JSON is `{"Swap":{"token_in","amount_in","path","min_amount_out","to"}}` or
   `{"AddLiquidity":{"token_in","amount_in","pool_id","tick_lower","tick_upper","min_liquidity"}}`. Keys are in
   that order and amounts are decimal strings. The intent is written with `JSON.stringify`, so the order is
   the signed bytes.
2. `POST <relay>/v1/intent` with `{"wallet","intent","nonce","expires","signature"}`. `intent` is the object, not a
   string. The reply is `{"txHash"?, "intentId"}`.
3. Send the input on Base Sepolia to the vault (`V4_VAULT_ADDRESS`). Native ETH by `sendTransaction`, test1 by
   `transfer`. A rejected deposit leaves the intent open: **Send deposit** retries, **Cancel intent** cancels.
4. The tracker polls `get_intent({id})` (Open, Executed{result}, Failed{reason}). For a swap, Executed is followed
   by the payout: the owner's withdrawal (`get_withdrawals_of_owner`) with the output token, the wallet as
   destination, and an id above the highest one before the swap. Basescan links are shown for the deposit and
   the payout.

Cancel: sign `Wind Swap v4 cancel intent <id> on <contract> by evm:0x<lower> nonce N expires T`, then
`POST <relay>/v1/intent/cancel` with `{"wallet","id","nonce","expires","signature"}`.

Copy used in the UI: NEAR, "Your tokens are refunded automatically if the price moves too much."; EVM, "If the swap
can't execute, your deposit stays in your Wind Swap balance — withdraw anytime."

Tokens: one-click uses the active chain's tokens. NEAR mode swaps and adds liquidity with NEAR tokens. EVM mode
uses the Base Sepolia assets (`base-sepolia:eth`, `base-sepolia:test1`), which `get_tokens` does not list, so the
market hook always includes them. `market.tokens` stays NEAR-only (deposits use it).

The one-click swap quotes `quote_exact_input` on the same path the intent uses. The zap's `min_liquidity` is an
estimate: half the input's liquidity in range (the zap swaps about half), the whole input out of range, less 1%.

## Contract v7 views used

| View | Used by |
|---|---|
| `get_position_of_owner`, `get_positions_of_owner` | Liquidity (position for a range), Rewards (positions, staked flag) |
| `get_stakes_of_owner` | Rewards (NFT id of each staked range) |
| `get_withdrawals_of_owner` | Bridge (withdrawal list) |
| `get_balances_of_owner` | Swap, Portfolio, Bridge, Lock (DEX balances, one call) |
| `get_bribe_tokens` | Vote (bribe token dropdown and bribe claims) |
| `get_gauges` | Vote, Rewards (gauge list, replaces probing pool ids) |
| `get_all_tokens_accounting` | Pools (Solvency panel) |
| `get_intent` | Swap and Liquidity one-click tracker (Open, Executed, Failed). The JSON shape is not in the spec, so `parseIntentState` accepts the bare status or `{status}`, a string or a one-key object |

When a view call fails, its card shows the readable error and the rest of the page still works. Nothing is
stored in the browser for these lists. Only the chosen EVM/NEAR mode is kept in localStorage.

## Notes and limits

- EVM mode, not covered (NEAR only): portfolio deposit and withdraw (NEP-141 `ft_transfer_call` and
  `withdraw`), and storage registration. These are not `SignedAction`s.
- Permanent lock: create it in one step with the **Permanent lock** checkbox on the Lock page (NEAR:
  `create_lock(amount, duration, permanent)`; EVM: signed `CreateLock` with `permanent: true`). An existing
  veNFT is made permanent with **Make permanent**.
- `distribute` is permissionless. NEAR mode sends it from the connected account. EVM mode signs `"Distribute"`.
- No EVM deposit path for WIND. The lock form draws on the DEX WIND balance. A NEAR account can deposit
  WIND with `ft_transfer_call`. The contract's deposit `msg` takes an `owner` wallet string, so a NEAR
  account can fund an EVM wallet this way. Not tested here.
- Solvency: `get_all_tokens_accounting` reads `migrated: true` until the owner runs `seed_pool_reserves`
  (pool-held amounts must be computed off-chain from pool state). Until then `pool_reserves` reads 0, and
  the panel shows a note.
- Exact-input swaps fail with `InsufficientLiquidity` when a pool cannot absorb the input. The message is
  shown as a sentence, not as the raw panic.
- Pools with tokens that are not whitelisted (`get_tokens`) are hidden. Pool 0 uses fake token ids, so it is hidden.
- Two-hop routes only exist when a pool path ends in a different token. With only tUSDC and tWETH,
  a two-hop route returns the input token, so no two-hop option is ever offered.
- Advanced swaps, two-token liquidity and withdrawals use DEX internal balances. Deposit from the wallet first. One-click swaps and zaps do not.
- Each token needs a storage registration for the user (`storage_deposit`, 0.00125 NEAR). The
  Portfolio page offers it when `storage_balance_of` returns null.
- The contract rounds amounts in the pool's favour. Liquidity amounts shown in the UI round down,
  so mint may need a small extra DEX balance.
- Not built or tested with wallets: signing in MetaMask, the relayer, the Bridge deposit flow on
  Base Sepolia, and EVM-mode mint, burn, collect, stake, distribute and bribe. Those need a human test
  before anyone relies on them.
- Not tested against a live relayer or contract: the one-click intent flow (`/v1/intent`, `get_intent` shape,
  the withdrawal matching for the payout), the NEAR `ft_transfer_call` swap and zap messages, and the zap's
  `min_liquidity` estimate. `npm run check:v4-intents` only checks the JSON and message strings.
- The one-click tracker lives in page state. A reload drops it, but the intent stays on chain (see Bridge for
  the withdrawal list).
- `npm run check:v4-intents` checks the one-step builders. Run it after changing `intents.ts`.
