# Wind Swap v4 on NEAR testnet

The `/v4` routes add the Wind Swap v4 DEX (NEAR testnet) next to the existing EVM pages. The
EVM pages are unchanged apart from one addition: Base Sepolia (84532) is in the wagmi chain list.
The NEAR wallet only loads under `/v4`. Under `/v4` the global chain guard does not switch the
wallet to Base, so a Base Sepolia deposit stays on Base Sepolia.

The v4 pages act for one of two wallets, chosen with the NEAR / EVM switch in the header:

- **NEAR**: a NEAR testnet account. Each action is a direct contract call from that account.
- **EVM**: a MetaMask (or other injected) wallet, for EVM-only users with no NEAR account. Each
  action is turned into a `SignedAction`, signed with `personal_sign`, and then sent to a relayer
  that calls `execute`. The relayer pays the NEAR gas.

The owner id (64 hex digits) is what the contract keys balances and veNFTs by. For a NEAR account
it is `sha256(account id)`. For an EVM wallet it comes from `resolve_wallet("evm:0x…")`.

## Pages

| Route | What it does |
|---|---|
| `/v4` | Swap tUSDC <-> tWETH. Route options: pool 1, pool 2, or best of all candidate routes. Live quotes via `quote_exact_input`. Slippage via SwapSettings. Swaps spend the DEX balance. |
| `/v4/pools` | Pools whose two tokens are whitelisted: pair, fee, tick spacing, price (token1 per token0), current tick, liquidity. |
| `/v4/liquidity` | Add liquidity by price range (min/max price -> ticks aligned to spacing), amounts derived from liquidity. Remove (`burn_position`), collect, and the position for the chosen range. |
| `/v4/portfolio` | NEAR only. DEX balances, wallet balances, storage registration status, deposit (`ft_transfer_call`, 1 yocto) and withdraw (1 yocto). |
| `/v4/bridge` | EVM only. Deposit ETH or test1 on Base Sepolia to the vault (`0xaa81…259e`), with a balance that updates when the relayer credits it. Withdraw with a signed `WithdrawEvm`, then track its status (Pending, Signed, Broadcast, Failed) with a Basescan link. |
| `/v4/lock` | Create a WIND lock (1 week to 4 years, rounded to weeks). For each veNFT: add WIND, extend, withdraw when expired, split, merge, make permanent. Shows voting power and whether it voted this epoch. |
| `/v4/vote` | Gauges of pools 1 to 10 (`get_gauge`), with each veNFT's votes, vote allocation (percent, total 100), reset, poke, fee and bribe claims, and a bribe form. |
| `/v4/rewards` | Epoch countdown (`get_epoch`) with a distribute button once the epoch has passed. Rebase claims per veNFT. Staked LP positions with claimable gauge rewards, stake, claim and unstake. |

`/v4` (Swap) works in both modes; its balances are read by owner. `/v4/liquidity` and `/v4/portfolio`
are NEAR only, and show a notice in EVM mode.

## Code layout

- `src/lib/windswap-v4/`: copy of the SDK source (`sdk/src`) at commit `e3e049a` of
  github.com/btb-finance/WindSwapV4. Import suffixes `.js` were dropped for the Next bundler.
- `src/lib/v4/config.ts`: contract id, RPC, token list, pool probe limit.
- `src/lib/v4/near.ts`: wallet-selector transaction conversion, `storage_deposit` action, readable error mapping.
- `src/lib/v4/routes.ts`: candidate routes (direct pools and two-hop pool routes).
- `src/lib/v4/evm/signed.ts`: `SignedAction` builders. `toSignedAction(call)` maps a NEAR method name to its
  variant with fields in the Rust declaration order. `actionMessage` builds the exact string the wallet signs.
- `src/lib/v4/ve/calls.ts`: ve(3,3) and swap/liquidity calls as `FunctionCallAction`s. The same call runs
  in NEAR mode (direct) or EVM mode (signed), depending on the active wallet.
- `src/lib/v4/ve/views.ts`, `loaders.ts`: read views for locks, gauges, epoch, claims, balances and withdrawals.
- `src/lib/v4/relay.ts`: POST to the relayer (see below).
- `src/providers/V4ActorProvider.tsx`: the active wallet (NEAR or EVM mode), owners, `run` (send or sign),
  and the last signed payload. `useV4Send` (swap, liquidity) routes through it.
- `src/components/v4/V4ModeSwitch.tsx`, `V4WalletGate.tsx`, `V4SignedPayload.tsx`: header switch, connect gate,
  and the copy-JSON panel for signed actions.
- `src/components/v4/V4Bridge.tsx`, `V4Lock.tsx`, `V4Vote.tsx`, `V4Rewards.tsx`: the new pages.
- `src/lib/v4/liquidity.ts`: price range to tick, amount to liquidity conversions.
- `src/providers/NearWalletProvider.tsx`: wallet-selector (My NEAR Wallet, Meteor, HERE), testnet.
- `src/app/v4/layout.tsx`: wraps the v4 routes with the NEAR provider and the v4 header.
- `src/hooks/v4/`: market (tokens and pools), balances, and send (pending state, errors, toasts).

## Config

Edit `src/lib/v4/config.ts`:

- `V4_CONTRACT_ID` (default `windswapv4-btb.testnet`)
- `V4_RPC_URL` (default `https://rpc.testnet.near.org`)
- `V4_TOKENS` (token account ids, symbols, decimals)
- `V4_POOL_PROBE_MAX` (pool ids probed on load; the contract has no pool count view)
- `V4_EVM_CHAIN_ID`, `V4_VAULT_ADDRESS`, `V4_TEST1_ADDRESS`, `V4_INTERNAL_TOKENS` (Base Sepolia bridge and token ids)

Environment:

- `NEXT_PUBLIC_V4_RELAY_URL` (optional): the relayer endpoint. Not built yet. Unset, every EVM action
  shows its signed payload with a **Copy relay JSON** button for an operator to submit. Never put a
  private key in the frontend.

## EVM mode: signing and relay

1. The wallet signs (EIP-191 `personal_sign`):
   `Wind Swap v4 action on windswapv4-btb.testnet by evm:0x<lower> nonce N expires T: <action JSON>`.
   The action JSON is `serde_json::to_string` of the contract's `SignedAction`: externally tagged, fields
   in declaration order, no spaces, amounts as strings. Example:
   `{"Vote":{"token_id":1,"pools":[4,1],"weights":["70","30"]}}`.
2. The nonce is unique per wallet (millisecond time plus a random part). `expires` is now + 600 s.
3. The relayer receives `POST NEXT_PUBLIC_V4_RELAY_URL` with
   `{"contractId":"windswapv4-btb.testnet","method":"execute","args":{"wallet","action","nonce","expires","signature"}}`.
   It calls `execute` with those args from a NEAR account it controls and returns
   `{"txHash"?, "result"?, "error"?}`. `result` is the contract's `ActionResult`. For `WithdrawEvm` it is
   `{"WithdrawEvm": <id>}`, which the Bridge page uses to track the withdrawal.

The signing path was checked outside the app: the canonical JSON of the sample actions matches the
Rust shape, and a signature from a test key recovers to its address.

## Notes and limits

- EVM mode, not covered (NEAR only): liquidity (mint, burn, collect), portfolio deposit and withdraw,
  storage registration, and `distribute` (it is not a `SignedAction`). `distribute` runs from any NEAR
  account. The Rewards page uses the NEAR wallet for it.
- No EVM deposit path for WIND. The lock form draws on the DEX WIND balance. A NEAR account can deposit
  WIND with `ft_transfer_call`. The contract's deposit `msg` takes an `owner` wallet string, so a NEAR
  account can fund an EVM wallet this way. Not tested here.
- Contract views missing for the UI:
  - `get_position` takes an `AccountId`, so EVM owners' positions cannot be read. The Rewards page
    tracks stake positions in browser storage (`windswap.v4.positions.<owner>`) because there is no list
    of stakes.
  - No view lists the whitelisted bribe tokens. The bribe form takes a token id.
  - No view lists withdrawals per owner. The Bridge page tracks ids it saw in browser storage
    (`windswap.v4.withdrawals.<owner>`), or ids added by hand.
- Creating a permanent lock is two steps: create the lock, then press **Make permanent** on the new veNFT.
- Gauges are found by probing pool ids 1 to `V4_POOL_PROBE_MAX`.
- Not built or tested with wallets: signing in MetaMask, the relayer, and the Bridge deposit flow on
  Base Sepolia. Those need a human test before anyone relies on them.


- Pools with tokens that are not whitelisted (`get_tokens`) are hidden. Pool 0 uses fake token ids, so it is hidden.
- Two-hop routes only exist when a pool path ends in a different token. With only tUSDC and tWETH,
  a two-hop route returns the input token, so no two-hop option is ever offered.
- Swaps, liquidity and withdrawals use DEX internal balances. Deposit from the wallet first.
- Each token needs a storage registration for the user (`storage_deposit`, 0.00125 NEAR). The
  Portfolio page offers it when `storage_balance_of` returns null.
- The contract rounds amounts in the pool's favour. Liquidity amounts shown in the UI round down,
  so mint may need a small extra DEX balance.
- Build: the Netlify build needs `NEXT_PUBLIC_CONVEX_URL` set (pre-existing requirement of `/admin`).
